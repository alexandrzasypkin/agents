# Astro 5 — Skill

## Stack

- **Astro 5** — framework built on Vite + TypeScript.
- **Adapter** — `@astrojs/cloudflare` (SSR on the Cloudflare Workers runtime).
- **Hosting** — Cloudflare (Workers / Pages).

## Project structure (conventional)

Astro is directory-driven. A typical layout:

```
src/
├── pages/                    # file-based routing
│   ├── index.astro           # a route
│   ├── *.astro               # rendered pages
│   └── api/
│       └── <route>.ts        # server endpoints (APIRoute handlers)
├── content/                  # Content Collections
├── components/               # .astro components + framework islands
├── layouts/                  # shared page shells
├── lib/
│   ├── server/               # edge/server-only code
│   └── shared/               # isomorphic utilities
├── middleware.ts             # request middleware (auth guards, etc.)
├── styles/
└── env.d.ts                  # binding + Astro.locals type references
public/                       # static assets (favicon, fonts, images)
astro.config.mjs
wrangler.toml                 # (or wrangler.jsonc)
package.json
tsconfig.json
worker-configuration.d.ts     # generated by `wrangler types`
```

A common convention is to separate a **public/static layer** (pure Astro render, no client JS) from an **interactive layer** (islands that hydrate).

## astro.config.mjs (minimal template)

```js
import { defineConfig } from "astro/config";
import cloudflare from "@astrojs/cloudflare";

export default defineConfig({
  output: "server",                  // "server" (SSR) or "static"
  adapter: cloudflare({
    platformProxy: { enabled: true } // exposes Astro.locals.runtime in `astro dev`
  }),
  vite: { /* build-time only — Node APIs allowed here */ }
});
```

- `output: "server"` renders every route on the Workers runtime (SSR). `output: "static"` prerenders at build time. In a mostly-server project you can still opt individual routes into prerendering with `export const prerender = true`.
- `platformProxy.enabled` makes Cloudflare bindings available locally during `astro dev` (proxies real Miniflare/workerd bindings into `Astro.locals.runtime`).

## Island hydration — directives

Astro ships zero JS by default. A component only ships/hydrates client JS when you add a `client:*` directive. Choose the latest (laziest) one that still gives the needed interactivity:

| Directive | When to use |
|-----------|-------------|
| `client:load` | Interactive immediately on first paint (rare; eager JS). |
| `client:idle` | Good default for non-critical islands — hydrates when the main thread is idle. |
| `client:visible` | Hydrates when the element scrolls into view (IntersectionObserver). Best below-the-fold. |
| `client:media="(...)"` | Hydrates only when a media query matches (e.g. mobile-only UI). |
| `client:only="<framework>"` | Skips SSR entirely — client-only render. Name the framework; provide a fallback. |

**Static/public content** should use no `client:*` at all — plain Astro render plus vanilla `<script>` and CSS. Reserve islands for parts that genuinely need client interactivity.

## Accessing Cloudflare bindings

In SSR pages and API endpoints, bindings (D1, KV, R2, secrets) are on `locals.runtime.env`:

```ts
// src/pages/api/example.ts
import type { APIRoute } from "astro";
export const GET: APIRoute = async ({ locals }) => {
  const env = locals.runtime.env;      // env.DB / env.MY_KV / env.MY_SECRET / ...
  return new Response("ok");
};
```

In a `.astro` frontmatter the same env is at `Astro.locals.runtime.env`. `runtime` also exposes `cf` (request geo), `ctx` (`waitUntil`/`passThroughOnException`), and `caches`. The type of `locals.runtime.env` comes from `worker-configuration.d.ts` — **regenerate with `wrangler types` after any change to `wrangler.toml`.** Bindings are NOT available in client-side islands — fetch through an API endpoint.

## env.d.ts

```ts
/// <reference path="../.astro/types.d.ts" />
/// <reference path="../worker-configuration.d.ts" />
type Runtime = import("@astrojs/cloudflare").Runtime<Env>;
declare namespace App {
  interface Locals extends Runtime { /* extra locals set by middleware */ }
}
```
`Env` is the global interface from `worker-configuration.d.ts`.

## Middleware

`src/middleware.ts` runs before every matching request — auth guards, redirects, populating `locals`:

```ts
import { defineMiddleware } from "astro:middleware";
export const onRequest = defineMiddleware(async (ctx, next) => {
  if (isProtected(ctx.url.pathname)) {
    // read a session via ctx.locals.runtime.env (D1/KV); set ctx.locals.user or return a redirect
  }
  return next();
});
```

## SSR vs static

- **SSR** (`output: "server"`): per-request handling on the Workers runtime; `Astro.request`, `Astro.locals.runtime`, cookies, bindings. Use for authenticated/dynamic pages and API routes.
- **Static / prerender**: HTML built once, no per-request runtime or bindings. Opt in per route with `export const prerender = true`.

## Pitfalls

1. `client:only` without a fallback — nothing renders until hydration; provide a slot fallback.
2. Importing server-only modules into an island — pulls server code into the client bundle; split `*.client.ts` / `*.server.ts` or move logic to an API endpoint.
3. `process.env` in the Workers runtime — not available; use `Astro.locals.runtime.env`.
4. Build-time vs runtime — `astro.config.mjs` runs on Node at build time; everything under `src/**` runs on workerd at request time (Web-standard APIs only).
5. Stale binding types — after editing `wrangler.toml`, re-run `wrangler types` or `env.MY_BINDING` is untyped.
