# i18n

The key namespaces are project-specific; this is the shared discipline.

## Two layers (do not overlap)
- **UI interface** (buttons, menus, forms, notifications, table headers) → locale files + `data-i18n` attribute binding.
- **Content pages** (About, Privacy, Terms, docs) → static text, NO `data-i18n`.
- **Backend-generated text** (emails, push/SMS/bot replies, API messages, server-rendered pages) → a locale-keyed template/resource picked by the recipient's locale; the mechanism is project-specific (not `data-i18n`), the discipline is identical — keyed, all locales, never a literal in code.

## Keys
- Dot notation, namespaced by context: `{section}.{category}.{key}` (e.g. `auth.errors.invalidEmail`, `layout.nav.home`).
- Not flat (`integrations`), not underscores (`auth_error`), not a camelCase full path (`cloudflareWizardTitle`).

## HTML binding family
`data-i18n` (plain text), `data-i18n-html` (text with tags), `data-i18n-aria`, `data-i18n-placeholder`, `data-i18n-title`.

## Discipline
[CRITICAL] A new key is added to **all** locales at once — never one locale only.

[CRITICAL] New user-facing text → a key in the locale/content layer, **never a literal in code and never one baked-in language** — holds for backend text (emails, replies) as much as the UI. (See `no-hardcode`.)
